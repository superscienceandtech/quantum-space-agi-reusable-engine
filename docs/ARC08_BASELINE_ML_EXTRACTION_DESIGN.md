# ARC-08 Exploratory Baseline Dataset Extraction Design

**Status: PROPOSED IMPLEMENTATION DESIGN — NOT DATASET OR SCIENTIFIC APPROVAL.** This document designs a reproducible extraction and audit workflow for the exploratory mass–radius proposal in [`ARC08_BASELINE_ML_TASK_SPEC.md`](ARC08_BASELINE_ML_TASK_SPEC.md). It does not authorize a NASA request, create a dataset, approve eligibility rules, or permit model fitting/training.

Candidate source: NASA Exoplanet Archive Planetary Systems (`ps`). Candidate output is `pl_bmasse`; candidate target provenance filter is `pl_bmassprov = 'Mass'`; candidate feature is `pl_rade`; `default_flag = 1` is a provisional parameter-set selection. These remain proposals pending scientific review.

## 1. Repository facts and extraction decision

### Verified current interfaces

- `fetch_ps_dataset()` in [`exoplanet_archive.py`](../src/quantum_space_agi/data/adapters/exoplanet_archive.py) calls the fixed synchronous endpoint, constructs `SELECT TOP ... FROM ps ORDER BY ...`, and accepts `limit` from 1 through the hard-coded `MAX_ROWS = 100`. It has no filter, pagination, or offset argument. It validates only the returned page for requested columns and supplied identity fields.
- The adapter reads the response with a byte cap, hashes exact response bytes, and records actual retrieval time, query, endpoint, table, output format, checksum, and selected ordering/identity fields. It then parses through `load_json()` and discards the response bytes. Archive release, DOI, table/column descriptions, units, and types remain unset in the adapter result.
- ARC-03 `Dataset` copies top-level record mappings but nested JSON values are mutable. `Provenance` records source, retrieval time, format, version, transformations, and metadata, with shallow metadata copying. `DataSchema`/`validate_dataset()` checks only explicitly declared presence, nullability, and exact Python types. `analyze_quality()` supplies structural missingness, exact duplicate-row groups, and finite numeric summaries; none of these establishes scientific eligibility.
- The current project has no durable raw response store, full-table extraction, pagination, or versioned mass–radius dataset schema. No dataset is present or generated by this design.

### Official TAP capabilities inspected

NASA's [TAP user guide](https://exoplanetarchive.ipac.caltech.edu/docs/TAP/usingTAP.html) states that the archive supports synchronous and asynchronous queries, recommends a TAP client for large data retrieval, documents ADQL `WHERE` constraints and JSON/VOTable/CSV/TSV formats, and documents querying `TAP_SCHEMA` for column names and types. The guide does **not** document a NASA-supported offset/page-token protocol or a numeric output ceiling. No live request was made for the original design; a separate controlled verification is recorded below.

**Recommended extraction shape:** one asynchronous TAP job for one complete, narrowly projected query, requesting VOTable. NASA documents VOTable as the default TAP output and confirms async service availability. VOTable is preferred because IVOA DALI requires `QUERY_STATUS=OVERFLOW` when a VOTable result is truncated; no standardized truncation marker is defined for CSV/TSV, and equivalent JSON signaling is not established here. See [IVOA DALI 1.1, overflow and errors](https://www.ivoa.net/documents/DALI/20170517/REC-DALI-1.1.html) and [IVOA TAP 1.1, MAXREC](https://www.ivoa.net/documents/TAP/20190927/REC-TAP-1.1.html). The controlled observations below verified successful small async jobs and `MAXREC` overflow signaling, but not full-scale limits or all truncation paths. A full extraction remains **blocked** until remaining behaviors are verified; if complete retrieval cannot be demonstrated, stop rather than use assumed paging.

Evidence labels in this design are deliberate: NASA documentation establishes what NASA publicly documents; IVOA Recommendations define protocol requirements; live observations establish only the specific behaviors tested. None establishes that the live NASA deployment advertises or conforms to every relevant capability/limit at full scale.

### Observed NASA Service Verification (2026-11-09)

This section records only two controlled, small live queries and one VOSI capabilities read against the official NASA Exoplanet Archive. It is service-behavior evidence, not dataset extraction. The query results were inspected in the terminal and were not saved as dataset artifacts or checksummed.

**Endpoint and service metadata**

- **Directly observed:** The repository adapter's synchronous endpoint is `https://exoplanetarchive.ipac.caltech.edu/TAP/sync`. NASA's live VOSI capabilities document at `https://exoplanetarchive.ipac.caltech.edu/TAP/capabilities` advertised the TAP base access URL `https://exoplanetarchive.ipac.caltech.edu/TAP`, TAP interface version `1.1`, ADQL `2.0`, and VOTable output (`application/x-votable+xml`, alias `votable`; it also listed `text/xml`, CSV, TSV, and IPAC). The async resource tested was `https://exoplanetarchive.ipac.caltech.edu/TAP/async`.
- **NASA documentation:** The [TAP user guide](https://exoplanetarchive.ipac.caltech.edu/docs/TAP/usingTAP.html) says the service supports synchronous and asynchronous queries and recommends TAP clients for large results. It identifies `/TAP/sync` for browser queries and `/TAP` as the client base URL.
- **Not advertised/NOT VERIFIED:** The live capabilities response contained no numeric `MAXREC`, maximum row count, response-byte cap, execution-duration limit, or other service ceiling. The inspected NASA guide does not state such numeric limits either. This does not prove that no operational limits exist.

**Queries and async behavior observed**

Both ADQL queries were submitted by HTTP POST to `/TAP/async` with `REQUEST=doQuery`, `LANG=ADQL`, and `FORMAT=votable`:

```sql
SELECT TOP 3 pl_name FROM ps ORDER BY pl_name
```

The first request set `MAXREC=10`; the second set `MAXREC=2`. These query-level `TOP 3` and row-limit values were deliberately small. No count query or candidate extraction query was run.

- **Directly observed:** Each submission returned HTTP `303` with a job URL. The first job (`tap_owbm0yba`) was observed in `PENDING`; a POST of `PHASE=RUN` returned HTTP `303`, and subsequent phase/job reads showed `COMPLETED`. The second job (`tap_4zm1bvbj`) also reached `COMPLETED` after the `RUN` request. The result URL was present in each completed UWS job document under its result entry and returned HTTP `200`. The first VOTable response had HTTP `Content-Length: 745`; the second had `682` bytes. No `QUEUED` or `EXECUTING` interval was observed, and no failure phase (`ERROR`, `ABORTED`, timeout, expiry) was induced or tested.
- **IVOA standard:** TAP defines asynchronous submission separately from execution/result retrieval; UWS defines job phases and transitions. The observations establish this service's behavior for these two jobs only, not its behavior for all phases or failure cases. See [IVOA TAP 1.1](https://www.ivoa.net/documents/TAP/20190927/REC-TAP-1.1.html) and [IVOA UWS 1.1](https://www.ivoa.net/documents/UWS/20161024/REC-UWS-1.1-20161024.pdf).

**VOTable structure and query status**

- **Directly observed, `MAXREC=10`:** The response was XML with a VOTable 1.3 root and exactly one `<RESOURCE type="results">`. Within that resource, one `<INFO name="QUERY_STATUS" value="OK"/>` appeared before the single `<TABLE>`. The table had one `FIELD` named `pl_name`, one `DATA/TABLEDATA`, and three rows. No trailing `QUERY_STATUS` was present. This successful tiny response matches the validator's accepted status structure when called with `expected_columns=("pl_name",)`.
- **Directly observed, `MAXREC=2`:** The response had the same root/resource/table shape, two table rows, and one initial `<INFO name="QUERY_STATUS" value="OVERFLOW"/>` before the table; no trailing status was present. The live response therefore signals this deliberately induced truncation in the initial status element.
- **IVOA-standard context:** [DALI 1.1](https://www.ivoa.net/documents/DALI/20170517/REC-DALI-1.1.html) defines `QUERY_STATUS=OVERFLOW` as a truncation signal and allows it as the initial status; when the initial status is `OK`, overflow is reported in a trailing status after the table. DALI also says output formats other than VOTable have no defined overflow signaling mechanism. The NASA observation is compatible with the initial-overflow form. It does not establish how the service reports other failures or non-MAXREC truncation.
- **Validator implication:** The offline validator's acceptance policy requires exactly one initial `QUERY_STATUS=OK` and rejects `OVERFLOW`, whether initial or trailing. It will reject the observed truncated response. This is intended fail-closed behavior; it must not require overflow to occur only as a trailing status.

**MAXREC and service limits**

- **Directly observed:** For the same `TOP 3` query, `MAXREC=10` returned three rows with `QUERY_STATUS=OK`; `MAXREC=2` returned two rows with initial `QUERY_STATUS=OVERFLOW`. Thus the service honored these requested limits in this small test and indicated truncation in VOTable. The job metadata echoed the requested `maxrec` values.
- **IVOA-standard context:** TAP requires a service to accept `MAXREC`, return no more than the requested number of records, and signal truncation when the result exceeds the effective requested/service limit. ADQL `TOP` constrains the query result; `MAXREC` constrains returned rows. See [TAP 1.1, MAXREC and overflow](https://www.ivoa.net/documents/TAP/20190927/REC-TAP-1.1.html).
- **Unresolved:** These two tests do not reveal the service's default `MAXREC`, maximum accepted/requested `MAXREC`, any lower server-side cap, byte limit, or behavior when those limits are reached. The VOSI capabilities response did not advertise numeric limits. No large `MAXREC` was tried.

**Extraction-design implications and remaining verification**

The official async endpoint and result URL flow worked for both tiny jobs, and the successful response's VOTable layout matched the expected one-resource/one-table/initial-OK shape. A small `MAXREC` truncation was observable and the validator's strict acceptance policy rejects it. These observations support continuing to use async VOTable for a future controlled extraction attempt, subject to the blocking checks below; they do **not** establish completeness at full scale.

Still unverified: NASA's effective/default/maximum `MAXREC`; any response-byte, row, execution-time, or result-retention ceiling; whether all service-side truncation modes produce a parseable VOTable overflow indication; UWS failure, timeout, and expiry behavior; stable snapshot semantics; and whether a later extraction will match a separate count. A candidate `COUNT(*)` query is documented below; it was not compared with extracted rows, and no snapshot-isolation claim is made. Before extraction, inspect capabilities again, verify any documented/advertised limits and relevant service behavior, and retain the exact raw result bytes for independent validation. If effective limits or completeness signaling cannot be established, keep extraction blocked. No rows from the two smoke tests constitute or validate the proposed ML dataset.

## 2. Architecture and data flow

```text

        |
        v
capture TAP_SCHEMA metadata + exact query manifest
        |
        v

        |

        |
```

Keep acquisition, raw artifacts, and scientific eligibility as distinct stages. Preserve original field values; produce derived normalized records separately.

## 3. Proposed query and retrieval protocol

### Query proposal

After the scientific reviewer approves the column set and provisional `default_flag` selection, use a query of this form (exact whitespace/order is stored as submitted):

```sql
SELECT pl_name, hostname, pl_refname, default_flag, soltype,
       pl_controv_flag, pl_bmasse, pl_bmassprov,
       pl_bmasseerr1, pl_bmasseerr2, pl_bmasselim,
       pl_rade, pl_radeerr1, pl_radeerr2, pl_radelim
FROM ps
WHERE default_flag = 1
ORDER BY pl_name, pl_refname
```

This is a **proposed query**, not executed or approved. It deliberately contains no ADQL `TOP`; a client-side row limit is not a substitute for completeness detection. Filtering only by the documented default flag retains non-`Mass` rows in the raw candidate response so the local eligibility ledger can record their exclusion. Do not add mass/radius/limit/controversy/solution predicates until the relevant semantics are verified and approved. `ORDER BY` aids readability but is not treated as a unique row key or a guarantee of snapshot stability.

### Async retrieval, VOTable completeness, MAXREC, and pagination comparison

1. Query `TAP_SCHEMA` and preserve the schema response before extraction; verify the listed columns, types, and table names against the approved query. NASA documents this metadata interface. It has not been queried in this task.
2. Submit the exact single ADQL query as an asynchronous TAP job using a compatible TAP client. A successful HTTP job-creation response/redirect and valid job reference prove only that the request was accepted for job handling; they do not prove query execution succeeded. The exact NASA submission response convention is not verified. Follow the [IVOA UWS 1.1 phase model](https://www.ivoa.net/documents/UWS/20161024/REC-UWS-1.1-20161024.pdf): poll `PENDING`, `QUEUED`, and `EXECUTING`; if `HELD`, follow UWS/client instructions to request execution or fail by policy; if `SUSPENDED`, continue bounded polling for resumption. `COMPLETED` is the only successful terminal execution phase. `ERROR` and `ABORTED` fail. Re-query `UNKNOWN` only within the bounded wait policy; unknown at timeout fails. `ARCHIVED` is not a successful execution phase and UWS permits results to have been deleted, so fail closed rather than assume a result remains available. A `COMPLETED` phase means job execution completed; it is **not** evidence that its result was not truncated.
3. After `COMPLETED`, retrieve the declared result URL. Require successful HTTP response, complete byte transfer, valid VOTable XML, and the expected query-result `RESOURCE`/`TABLE`. Missing/unavailable result URL, non-success HTTP status, interrupted transfer, malformed XML, absent/ambiguous result resource, or parse failure invalidates the attempt. Never treat the submission response or UWS job metadata document as the result table.
4. Inspect every `INFO` named `QUERY_STATUS` in the query-result resource, including any status after the table. IVOA DALI requires an initial status before the table and permits a trailing `OVERFLOW` or `ERROR` to report a condition discovered while streaming. The only accepted status sequence is one initial `OK` before the table and no trailing query-status element. Any `QUERY_STATUS=OVERFLOW` is an extraction failure and the rows are not a usable complete dataset. Initial `ERROR`, trailing `ERROR`, missing status, malformed status, unknown values, duplicate/conflicting statuses, or multiple ambiguous query-result resources are failures, not assumed success. Preserve the raw VOTable bytes and status parse in the manifest. A status of `OK` does not by itself prove the result was complete if NASA applies a non-standard truncation or byte cap; service-specific behavior must be verified.
5. Do not request an arbitrarily large `MAXREC` and assume it removes limits. Under IVOA DALI, the service may apply a default limit when `MAXREC` is omitted and may enforce an effective maximum lower than the requested value; if the result is truncated because of that limit, it must indicate overflow. TAP 1.1 specifies that this `MAXREC` truncation is applied after query limitations such as ADQL `TOP`: if `TOP` is lower, that many rows may be returned without an overflow indication. Thus `TOP` is a query-level cap and `MAXREC` is a result-row cap; neither alone proves that all predicate-matching archive rows were returned. The extraction query omits `TOP`. Before full extraction, inspect available NASA service capabilities/resource-limit metadata (including any advertised output-row limit, hard cap, async support and formats), verify the effective `MAXREC`, and verify VOTable overflow behavior and any independent response-byte ceiling. NASA's published guide documents TAP_SCHEMA but does not establish these live limits. If effective limits or overflow behavior cannot be verified, extraction remains blocked.
6. Run a separate `SELECT COUNT(*)` query using the exact same candidate `WHERE` predicate (currently `default_flag = 1`) as an independent consistency diagnostic. Record its exact ADQL, retrieval time, result and checksum. Its own VOTable must have the accepted `QUERY_STATUS` sequence, parse to exactly one row and one valid non-negative integer count, and have no overflow. A failed/missing/malformed count result means the required consistency check did not pass. A count mismatch with parsed rows fails acceptance; retain the attempt as incomplete and investigate or repeat the entire extraction as a new snapshot. Matching counts are useful evidence but do not prove the queries observed the same archive state: archive changes may occur between the count and result queries. No source inspected establishes transactional snapshot isolation for these separate requests, so never claim it. Document that limitation even when counts match.
7. After these checks, independently recompute SHA-256 from the saved response bytes and compare it with the manifest. Re-read and parse the saved artifact, verify required schema/columns, record count, and status results. If there is a required count check, it must match or its explicitly approved limitation must be documented; this design's default is to require a match and still disclose the lack of snapshot isolation.

**Pagination alternatives:**

| Method | Evidence and decision |
| --- | --- |
| `OFFSET` or page token | Not documented in the NASA TAP guide inspected. Do not use or recommend as supported. |
| Repeated `TOP` pages | `TOP` is a query-level cap, not a page boundary. Increasing `TOP` does not prove no omissions/duplicates across a changing archive. Do not use as pagination. |
| Deterministic disjoint ADQL partitions | `WHERE` predicates are supported generally, but no stable unique partition key/range and archive snapshot-isolation behavior has been verified for this extraction. Keep only as a future fallback design requiring its own verification; do not implement or use now. |
| One async query with VOTable | NASA confirms async queries and recommends TAP clients for large retrievals; IVOA standards define VOTable query-status overflow signaling. Preferred candidate, conditional on verifying NASA's effective limits and status behavior before full extraction. |

## 4. Snapshot, manifest, and provenance layout

Store raw source artifacts outside Git in an approved durable location. Proposed layout:

```text
data/raw/nasa_exoplanet_archive/ps/mass_radius/<snapshot_id>/
  manifest.json
  tap_schema.xml
  query.adql
  response.votable
  integrity.json
  eligibility_ledger.jsonl
  normalized_records.jsonl
  grouping_report.json
  audit_report.json
```

`response.votable` is the exact byte stream returned by the service, not a re-serialized parsed table. `tap_schema.xml` is the captured schema response if the documented TAP tables endpoint is used; if using a `TAP_SCHEMA` query, preserve its exact query and raw response instead. Never overwrite an existing snapshot. A snapshot is immutable after finalization; a re-fetch creates a new snapshot directory. The current ARC-03 `DataFormat`/`load_json()` APIs do not parse VOTable. Any later conversion to ARC-03 `Dataset` must be a separately reviewed derived artifact with an explicit schema and type/null mapping; it must not replace the retained source VOTable or change ARC-03 APIs as part of this design.

### Naming and checksum policy

- Define `snapshot_id` from UTC retrieval timestamp plus a prefix of SHA-256 over the exact ADQL bytes, for example `20261109T120000Z_<query-sha256-prefix>`. Timestamp distinguishes reretrievals of an identical query; query digest distinguishes query revisions. The response checksum is separate and identifies the actual returned bytes.
- Save the exact ADQL as UTF-8, with a trailing newline policy fixed in the manifest; hash the exact query bytes that were submitted after declared encoding.
- Compute SHA-256 on the raw response bytes before decoding. Record full lowercase hex digest and byte length in `manifest.json` and `integrity.json`. On every later read, recompute and compare; a mismatch invalidates the snapshot.
- A checksum verifies byte identity but cannot reconstruct absent bytes. Back up the raw response and manifest under the approved retention policy.
- Do not use a checksum or timestamp as a claimed NASA release/snapshot identifier. No stable archive release is currently returned by the adapter.

### Required manifest fields

Record archive name, TAP base/endpoint and protocol mode, table (`ps`), exact ADQL and query SHA-256, requested VOTable format, selected columns, ordering, provisional extraction-policy ID, submission/job-completion/result-retrieval timestamps, job ID and phase history, result URL, response byte count and checksum, parsed row count, independent count query/result/time, schema metadata artifact path/checksum, code revision, tool/client and version, timeout/retry configuration, requested and effective `MAXREC`/output limit (or `unknown`), VOTable `QUERY_STATUS` sequence, completeness/truncation evidence, and known archive release/version (explicitly `null` if unavailable). Include source citation/acknowledgement guidance as metadata. No secrets or credentials belong in the manifest.

ARC-03 `Provenance` can hold source, UTC retrieval timestamp, JSON format, and metadata, but is shallow for nested values and cannot itself preserve raw bytes. For any later `Dataset`, reference the immutable snapshot ID, raw response checksum, query and policy/schema IDs in provenance metadata. Do not treat a constructed `Dataset` as the raw artifact. Do not claim a value for unknown archive release or source DOI.

## 5. Parsing, eligibility ledger, and data-quality report

### Mechanical checks vs. scientific decisions

**Mechanically safe once the response is retained:** verify checksum/length; parse without coercion; report absent fields separately from JSON `null`; reject malformed record structure; check exact wire types against captured schema; identify non-finite values; preserve the original record; record each validation result. The existing adapter already rejects non-finite JSON numbers and absent requested fields for its bounded response, while JSON nulls are preserved. ARC-03 schema checks can be reused but do not cover numeric range, flags, units, or scientific validity.

**Not authorized until verified/reviewed:** excluding by `pl_bmasselim`, `pl_radelim`, `pl_controv_flag`, or `soltype`; interpreting missing flags; deciding whether zero/negative measurements are valid; requiring uncertainty fields; resolving conflicting or duplicate parameter sets. No unverified code mapping may be applied.

### Eligibility decision ledger

Create one ledger entry for each source record, linked to the immutable snapshot by response-relative row ordinal and a hash of its canonical source-record representation. Preserve the original record in the raw snapshot. Ledger fields should include `snapshot_id`, source row ordinal, row fingerprint, `pl_name`, `hostname`, `pl_refname`, each named check's `pass`/`fail`/`unresolved` state, all applicable reason codes, and a final eligibility state. A record with unresolved scientific checks is `pending_review`, not eligible.

Report both (a) counts for every individual reason, which may overlap, and (b) an exclusive primary disposition using a published fixed precedence. Never sum overlapping reason counts as if they were unique excluded rows. Keep raw nulls and raw flag/category strings in the record and ledger.

### Required quality summary

Report total raw rows, parsed rows, records by raw flag/category value including null, selected candidate count after each approved mechanical rule, pending-review rows, eligible rows after all approved scientific rules, and excluded rows. For each selected field report present/absent/null/blank counts, observed JSON/Python types, invalid-type counts, and non-finite counts. The current adapter rejects non-finite JSON constants/exponent overflow before returning a `Dataset`; still include response parse errors and field-level audit failures in the extraction report. Report exact duplicate rows and duplicates under each proposed identity key separately; do not infer that all duplicates are errors.

Use `validate_dataset()` only with a reviewed versioned schema. Use `analyze_quality()` as an additional summary, not as a substitute for the explicit per-field ledger or scientific review. Keep report counts tied to the snapshot ID and schema/policy versions.

## 6. Identity, reference overlap, and grouping

1. **Missing identity:** report missing/null/blank `pl_name`, `hostname`, and `pl_refname` separately. Rows lacking `pl_name` cannot enter a planet-level cohort; rows lacking `hostname` or `pl_refname` cannot enter the proposed leakage-safe grouped evaluation. Quarantine them with explicit reasons pending policy approval.
2. **Planet audit:** count distinct raw and eligible `pl_name` values, duplicate selected rows per name, conflicting `hostname` values per name, and multiple references per name. Never resolve a collision by query ordering or by choosing the value that improves fit.
3. **Host audit:** count planets and records per `hostname`; repeated planets on a host are expected to form one indivisible group. Audit normalization/case only under an approved deterministic rule; do not merge aliases speculatively.
4. **Reference audit:** count distinct and repeated `pl_refname` values and list references linked to multiple hosts. Keep the original reference text; any normalization needs a documented rule.
5. **Connected components:** build a bipartite graph with separate node namespaces `host:<hostname>` and `ref:<pl_refname>`. Each eligible row adds an edge between its host and reference node. Compute components deterministically (sorted nodes/edges) using DFS/BFS or union-find; assign every row/host/reference in a component to one partition. Verify by assertion that neither host nor reference crosses partitions.
6. **Stop conditions:** stop before fitting if graph construction has unresolved/missing identities; unresolved duplicate planets; a giant component or component-size imbalance prevents useful partitions; too few components remain for train/validation/test; or a non-empty test set cannot be formed under preapproved group-count/size rules. Quantitative thresholds and partition proportions are **NOT SPECIFIED** and require approval before inspecting model metrics. Never break components and never silently fall back to random row splitting.

No group counts or component sizes are asserted here; calculating them requires the future retained dataset, which has not been generated.

## 7. Failure, retry, and recovery

- Treat each stage separately: HTTP submission accepted; UWS job reached `COMPLETED`; result retrieval finished successfully; VOTable parse/status/schema/checksum/count checks passed. Failure at any later stage does not become success because an earlier stage succeeded.
- Use finite connect/read/job-wait timeouts and a bounded polling interval. Exact duration and retry count require service-behavior testing and approval; the current sync adapter's 20-second timeout is not automatically suitable for asynchronous full-table extraction. On job-wait timeout, stop polling, record the last phase and attempt state as incomplete; do not accept any available partial result.
- For `ERROR` or `ABORTED`, preserve a failure manifest and diagnostics, do not retrieve or accept result artifacts even if a result link exists, and investigate the service error. For `UNKNOWN`, re-query within the bounded polling policy; if it remains unknown, fail closed. If the job expires/enters `ARCHIVED`, or its result URL is missing/unavailable, mark the snapshot failed/incomplete and submit a new job only as a new attempt after the failure is understood.
- If result download is interrupted, HTTP transfer fails, or expected byte length/transfer completion cannot be established, do not parse/accept the partial file. Delete only a temporary partial artifact under the future writer's atomic-write policy; retain attempt metadata and retry the whole result retrieval only if the same completed job/result remains available and the retry policy allows it. Never splice bytes from separate retrieval attempts.
- Reject VOTable `QUERY_STATUS=OVERFLOW` even when the job phase is `COMPLETED`, a `COUNT(*)` appears to match, or the table parses. Reject missing, malformed, unknown, or ambiguous query-status metadata. A separate count match cannot override a protocol overflow status.
- Retry only transient transport errors, HTTP 5xx, or documented temporary service-unavailable states, with bounded exponential backoff and jitter if an async client supports it. Do not retry invalid ADQL, TAP query rejection, authentication/authorization errors, schema/type failures, malformed VOTable, or checksum mismatch without changing and versioning the request/policy.
- Persist separate manifest states such as `submission_accepted`, `job_completed`, `result_downloaded`, `artifact_accepted`, `failed`, and `incomplete`; only `artifact_accepted` means all checks below passed. Save job identifiers and safe diagnostics without credentials.
- Write response to a temporary file in the target snapshot directory, flush/close, verify length/checksum and parse/completeness, then atomically finalize the artifact and manifest. Never expose a partial response as a valid dataset. If the job fails or the response is truncated, retain a failure manifest/log if policy allows, mark the snapshot incomplete, and restart as a new attempt; do not concatenate partial responses.
- For any future verified partition approach, maintain a manifest per disjoint partition, require every partition to reach complete state, check expected boundaries and row identities across all partitions, and publish a combined snapshot only after all checks pass. A failed partition blocks the combined snapshot; no silent partial dataset.

## 8. Implementation phases and tests

### Raw artifact acceptance criteria

A raw response may be marked `artifact_accepted` only when every applicable condition is satisfied:

1. The async submission was accepted and the associated UWS job reached `COMPLETED`; `ERROR`, `ABORTED`, unresolved `UNKNOWN`, timeout, or expired/archived job fails.
2. The result URL was available and the complete response download finished successfully; no interrupted or partial transfer is accepted.
3. The saved raw VOTable parses as a complete XML document and contains one unambiguous query-result resource/table with all required columns and schema-compatible fields.
4. The VOTable contains exactly one initial `QUERY_STATUS=OK` before the table and no trailing/duplicate status; it contains no `OVERFLOW`, `ERROR`, unknown, malformed, or ambiguous status. `COMPLETED` alone is insufficient.
5. Any required independent `COUNT(*)` consistency check passes; the manifest still documents that a matching separate count does not establish snapshot isolation.
6. SHA-256 recomputed from the saved exact bytes matches the manifest digest and byte count. The saved artifact can be re-read and validated.
7. Effective `MAXREC`, service output limits, and NASA's actual overflow/status behavior for the selected async format have been verified sufficiently to rule out undocumented truncation. If not, the response remains unaccepted even if all other checks pass.

If a required check is unavailable or ambiguous, mark the attempt `incomplete`/`blocked`, preserve the diagnostic manifest, and do not pass its rows to eligibility processing as a complete candidate dataset.

Implementation proceeds only after scientific eligibility and acquisition decisions are approved.

1. **Acquisition spike:** the two-row/three-row async and `MAXREC` smoke checks above are complete. Before a candidate extraction, verify any advertised/effective service row and byte limits, default/maximum `MAXREC`, status signaling at relevant limits, TAP schema retrieval, the approved count-query behavior, and result expiry/failure handling. Record standards requirements separately from NASA-live observations. If completeness cannot be established, stop and redesign.
2. **Snapshot writer and manifest:** implement deterministic paths, atomic writes, exact-byte hashing, integrity verification, and incomplete-state handling. Tests use mocked TAP/client responses and local temporary directories.
3. **Schema/parse adapter:** capture schema metadata and parse the retained raw response without changing ARC-03 APIs. Test nulls, numeric types, missing fields, invalid types, non-finite values, malformed/truncated response, and schema drift.
4. **Eligibility ledger and report:** implement only approved mechanical/scientific rules, preserving source values and per-reason counts. Test every rule boundary and overlapping/exclusive counts.
5. **Identity/group audit:** implement duplicate and cross-reference diagnostics and deterministic host-reference connected components. Test missing IDs, duplicate planets, repeated hosts/references, disconnected components, giant component stop, deterministic output, and no host/reference crossing.
6. **End-to-end dry run:** use a small archived or mocked fixture only; verify query/manifest/checksum/ledger/report consistency and recovery from failures. This does not substitute for a later approved full dataset extraction.

No tests or source implementation are added by this design document.

## 9. Decisions still required

- Scientific approval of the task, prediction interpretation/timing, `default_flag` selection, exact target and feature eligibility, and meaning of the `Mass` category for the intended question.
- Authoritative current `ps` types/nullability and raw category values; limit code mappings; uncertainty, solution, controversy, zero/negative, missingness, and duplicate policies.
- A verified async result format and completeness/truncation protocol, service resource limits, TAP client/dependency choice, and bounded timeout/retry settings.
- Further NASA-live verification of failure/expiry phases, effective/default/maximum `MAXREC`, and any independent row/byte cap remains outstanding. The two small requests verified successful submission/run/completion/result retrieval and observed both `OK` and `OVERFLOW` VOTable statuses, but do not establish full-scale completeness or the absence of other truncation paths. These remain blockers; standards requirements and tiny-query observations do not prove the NASA deployment's full-scale behavior.
- Whether a separate `COUNT(*)` query is required, how count mismatch is handled, and explicit acknowledgment that separate queries are not proven to share a transactionally consistent snapshot.
- Durable storage location, retention/access policy, whether raw response artifacts may be kept outside the repository, and citation/terms review.
- Grouping choice (host only or host-reference components), identity normalization, component stop thresholds, train/validation/test proportions and seed.
- Dataset/schema/filter-policy version identifiers, final exclusion accounting, baseline and metric protocol, and acceptance threshold.

Until these are resolved, extraction and ML remain **NO-GO**. This proposal is not an authorization to access NASA data and makes no claim of dataset readiness or scientific validity.
