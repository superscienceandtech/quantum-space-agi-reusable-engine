# ARC-08 Scientific Eligibility Policy Review

**Status: EXPLORATORY POLICY REVIEW — NOT SCIENTIFIC APPROVAL.** This document consolidates recorded evidence and provisional handling for the proposed NASA Exoplanet Archive mass–radius baseline. It does not approve the task, cohort, extraction, evaluation, or training.

**Scope:** `ps` table; proposed target `pl_bmasse`; proposed cohort `default_flag = 1 AND pl_bmassprov = 'Mass'`; proposed sole feature `pl_rade`. The educational mission evaluator and its fictional score are unrelated and must not be used as training labels.

## Status labels

- **documented:** directly stated by a cited NASA source or verified in the repository.
- **proposed:** recommended handling only; not an approved scientific inclusion rule.
- **unresolved:** evidence does not settle the issue.
- **requires_scientific_approval:** a project scientific-owner decision is required before the rule is used to define an eligible cohort or evaluation.

These labels may appear together: a technical fact can be documented while its scientific use remains proposed or unresolved.

## Technical validation versus scientific eligibility

### Technical checks that can be prepared independently

After an approved artifact is available, the following can be implemented as audit mechanics without assigning scientific meaning:

- Preserve original JSON values, nulls, strings, and row order/provenance; distinguish absent fields, explicit null, blank text, wrong type, and non-finite values.
- Check exact expected columns/types against a versioned source schema; report rather than silently coerce.
- Count candidate predicate matches and raw categories, and compute deterministic exact-string duplicate/identity and group-overlap reports.
- Emit per-row check results (`pass`, `fail`, `unresolved`) and stable reason codes, while unresolved checks prevent a row being labeled eligible.
- Validate that proposed feature input contains only the approved candidate feature and excludes target-derived values and identifiers.
- Use ARC-03 `validate_dataset()` and `analyze_quality()` for their documented structural/quality functions only; do not reinterpret them as scientific readiness checks.

The current ARC-03 adapter cannot produce the complete retained snapshot described by the extraction design: it is limited to 100 JSON rows, has no filter or pagination interface, hashes but does not retain raw response bytes. No full dataset extraction is authorized by this review.

### Scientific decisions that must remain blocked

Do not finalize positive/negative or limit-based eligibility, uncertainty selection/weighting, controversy or solution-type filtering, identity normalization/deduplication, host/reference split policy, physical-domain bounds, or acceptance thresholds until the required scientific-owner decisions and evidence are recorded. Do not call the 2,211-row candidate count the eligible dataset size. Do not train or evaluate a model.

## Decisions required from the scientific owner

1. Approve, revise, or reject the mass-from-radius research question, intended interpretation, prediction unit, and timing.
2. Confirm whether the default `ps` parameter set and exact `pl_bmassprov='Mass'` restriction match the intended target population.
3. Decide how to handle zero/negative values and any verified limit/censored records; first obtain authoritative active-`ps` meanings for `pl_bmasselim` and `pl_radelim`.
4. Decide whether uncertainty fields remain descriptive metadata, define any sensitivity analysis, and prohibit unsupported weighting/feature use.
5. Decide whether/how `pl_controv_flag` and `soltype` affect inclusion, including null and unfamiliar values.
6. Approve duplicate-name resolution and missing/ambiguous planet, host, and reference identity handling; no silent deduplication or normalization.
7. Approve host-only versus host-reference connected-component grouping, split proportions/minimum group criteria/seed, and stop conditions based on actual group diagnostics.
8. Approve the durable raw snapshot/manifest, retention and access approach, citation obligations, schema/filter-policy versions, and any baseline/metric acceptance criterion before final test results are inspected.

## Safe implementation boundary

**May proceed without resolving scientific cohort decisions:** offline validators, field-presence/type/null/non-finite reporting, lossless row preservation, deterministic duplicate and identity diagnostics, synthetic-fixture ledger/report tests, and structural feature allowlist checks. These outputs must label unresolved fields and must not claim eligibility.

**Must remain blocked:** full NASA candidate extraction; code-based limit filtering; zero/negative physical cutoffs; uncertainty-based filtering, weights, or features; controversy/solution filters; deduplication/identity normalization; final cohort publication; selecting an actual grouped split; model fitting/evaluation/training; and all performance or scientific-validity claims.

Overall readiness remains **NO-GO** for dataset extraction and ML execution until the relevant source-completeness and scientific approvals are in place.
